# Лабораторная работа №3. ScyllaDB

Вариант №7809. Продолжение приложения лабораторных №1 и №2.

## 1. Задание и сохранение функциональности

Требуется подключить wide-column хранилище ScyllaDB для событий выполнения бизнес-операций, сохранить существующие CRUD API и хранилища, развернуть три узла с RF=3. Обязательная выборка: события с заданным результатом за период. Временной бакет составляет один день. Назначенный сценарий: запись ONE, чтение QUORUM, остановка одной реплики, исследование образования и удаления tombstones. Для нагрузки измеряются throughput, средняя задержка и p95.

За основу взят исходный код соседней лабораторной №2. Постоянные объекты и документы с ревизиями остаются в CouchDB, временные заявки с TTL, счетчики CAS и кэш настроек остаются в Etcd. Сохранены контроллеры, сервисы, CouchDB validation function, MapReduce, Mango-индексы и репликация. PostgreSQL был заменен CouchDB еще в работе №2; новая работа не удаляет прежние базы. Compose использует отдельные volumes проекта lab3.

Новый раздел интерфейса «Бизнес-операции» позволяет выбрать результат, операцию или объект, период, направление сортировки и размер страницы. Старые разделы создания событий, заявок, заказов и настроек сохранены.

## 2. Архитектура и модель события

Приложение работает на Java 17 и Spring Boot. ScyllaDB 6.2.3 развернута в трех контейнерах. Каждый узел использует один shard и 768 MiB памяти, developer mode и overprovisioned. Это учебные параметры, а не конфигурация промышленного сервера. Все узлы относятся к datacenter1, rack1. NetworkTopologyStrategy задает RF=3. При трех узлах каждый раздел хранится на всех трех репликах. У каждого узла отдельный volume.

HTTP interceptor записывает результат изменяющей бизнес-операции после завершения обработчика. ResponseBodyAdvice извлекает ID созданного объекта, не меняя тело ответа. Обрабатываются CREATE_EVENT, UPDATE_EVENT, DELETE_EVENT, REGISTER_VIEW, CREATE_DRAFT, SUBMIT_DRAFT и SAVE_SETTINGS. Результат SUCCESS соответствует HTTP-коду ниже 400, FAILURE - ошибке. GET-запросы и технический эксперимент CAS не включаются. Повторная отправка одной заявки является новой попыткой операции и новым событием, но существующий заказ сохраняет прежний ID.

| Поле | Содержание |
| --- | --- |
| event_id | Уникальный timeuuid; также определяет порядок |
| day | Календарная дата UTC, вычисленная из event_id |
| result | SUCCESS или FAILURE |
| operation | Название выполнявшейся операции |
| entity | ID объекта; для submit - ID заявки |
| http_status | Результирующий HTTP-код |
| duration_ms | Время обработки до записи аудита |

occurredAt в JSON вычисляется из timeuuid и возвращается в UTC. Для неуспешного создания без ID используется entity=collection. Имена менеджеров не являются аутентифицированными пользователями. Это учебное приложение без публичного доступа.

Запись трех копий события выполняется logged batch с ONE. При повторе используется тот же первичный ключ. Batch помогает завершить денормализованную запись после частичного сбоя, однако не делает чтение разных разделов изолированным. Общей транзакции между CouchDB, Etcd и ScyllaDB нет. Если аудит недоступен полностью, уже выполненная бизнес-операция не превращается в ошибку: сбой пишется в лог и увеличивает failed в /api/business-events/status. Без durable outbox часть событий при полном отказе или падении процесса может потеряться. Этот предел реализации явно отделен от эксперимента с одной остановленной репликой.

## 3. Таблицы от запросов и бакетирование

Для каждого из трех запросов создана собственная таблица. Полный DDL находится в scylla/schema.cql. Серверные выборки всегда задают весь partition key и диапазон clustering key. Фильтрующая директива, вторичные индексы и сканирование таблицы не используются.

| Запрос | Таблица | Partition key | Clustering key |
| --- | --- | --- | --- |
| Результат за период | by_result | (result_key, day) | event_id DESC |
| Операция за период | by_operation | (operation_key, day) | event_id DESC |
| История объекта | by_entity | (entity_key, day) | event_id DESC |

Составной partition key локализует один тип выборки в пределах одного UTC-дня. Без day история одного результата могла бы расти неограниченно в одном разделе. Дневной бакет ограничивает временной охват, но не число событий: при большой интенсивности SUCCESS остается горячим разделом. Следующим шагом масштабирования могло бы стать добавление shard к ключу с объединением отсортированных потоков. Для данной работы это не требуется.

timeuuid содержит время и уникальную часть. Поэтому два события с одинаковым временем в миллисекундах не перезаписывают друг друга и имеют устойчивый порядок. Полезная нагрузка дублируется трижды на уровне таблиц; RF=3 дополнительно реплицирует каждую копию. Это осознанная плата за прямые запросы.

Пример CQL внутри одного бакета:

```sql
SELECT event_id,result,operation,entity,http_status,duration_ms
FROM business_events.by_result
WHERE result_key=? AND day=?
  AND event_id >= ? AND event_id < ?
ORDER BY event_id DESC LIMIT ?;
```

## 4. API, сортировка и пагинация

Новый маршрут GET /api/business-events требует ровно один фильтр result, operation или entity. from включается, to исключается; оба значения являются ISO-8601 временем с часовым поясом и точностью до миллисекунд. Максимальная длительность периода - 31 день. В зависимости от времени начала такой интервал затрагивает до 32 календарных бакетов. sort принимает asc или desc, limit - от 1 до 200.

Пример: /api/business-events?result=SUCCESS&from=2026-11-11T00:00:00Z&to=2026-11-13T00:00:00Z&sort=desc&limit=20.

Сервис обходит дни в порядке сортировки и запрашивает не более оставшегося размера страницы плюс одну строку. Дополнительная строка позволяет определить наличие следующей страницы. Курсор хранит полный timeuuid последнего выданного события, фильтр, границы и направление. Продолжение внутри дня использует строгое сравнение с этим timeuuid; затем сервис переходит к следующему дню. Пустые дни пропускаются. OFFSET не используется, уже выданные строки повторно не загружаются.

Ответ содержит events и nextCursor. null означает завершение. Изменение фильтра или сортировки при сохраненном курсоре дает 400. Курсор не является средством авторизации и не подписан; изменение его позиции эквивалентно переходу внутри разрешенного публичного учебного диапазона. При параллельных новых записях выборка не является снимком: событие, вставленное за пройденной позицией, может не попасть в продолжение.

Интеграционные тесты проверяют все три таблицы, оба направления, исключение верхней границы, пустой день, совпадающие миллисекунды и страницы по одной записи. Дополнительно проверяется появление конкретных новых успешных и неуспешных операций по уникальным ID, а не наличие исторических событий.

## 5. Уровни согласованности и отказ реплики

При RF=3 уровень ONE требует одну реплику, QUORUM - две, ALL - три. Назначенная пара ONE/QUORUM имеет W+R=3, а для гарантированного пересечения требуется W+R>RF. Поэтому нельзя обещать read-after-write consistency. Запись рассылается репликам, но подтверждение ONE может прийти раньше обновления тех двух реплик, которые ответят на чтение. QUORUM/QUORUM обеспечивает пересечение множеств подтверждения в обычном сценарии, но не является общей транзакцией и не заменяет LWT.

Скрипт scylla_experiments.py выполняет пары ONE/ONE, ONE/QUORUM, QUORUM/QUORUM, ALL/ALL, затем останавливает scylla3, ожидает состояния 2 UN + 1 DN и повторяет те же пары. После старта scylla3 проверяется 3 UN и повторяется ONE/QUORUM. В каждом измерении 300 записей и 300 чтений, 8 потоков, отдельный уникальный ключ; прогрев не входит в статистику. Перед чтениями существует начальная запись, подтвержденная QUORUM. Это сравнение доступности и задержки, а не тест отсутствия устаревшего чтения.

Python-клиент работает внутри scylla1, использует подготовленные запросы и FallthroughRetryPolicy, без повторов после ошибок. Один write - logged batch из трех INSERT; один read - до 50 строк таблицы by_result. CQL-замеры не включают HTTP, CouchDB и Etcd. Средняя и p95 включают неуспешные попытки; throughput учитывает только успешные. p95 - элемент отсортированного массива с рангом ceil(0.95*N).

Меньшая задержка отдельных измерений после отказа не доказывает, что отказ ускоряет систему: каждый короткий прогон зависит от прогрева, планирования потоков, фоновой работы и состояния VM. Все три узла используют один физический компьютер, поэтому эксперимент моделирует остановку процесса-реплики, а не потерю независимого сервера или площадки. Сырые значения всех попыток и nodetool status сохранены в output/evidence/consistency.json.

## 6. Образование и удаление tombstones

Удаление в LSM-хранилище записывает tombstone с временем удаления. Старое значение еще может находиться в неизменяемом SSTable или на другой реплике. Чтение учитывает маркер и скрывает значение, но логическое исчезновение строки не доказывает физическое освобождение места. Compaction объединяет SSTables и может удалить устаревшие данные вместе с tombstone при выполнении условий сборки мусора.

В изолированной таблице создано 100 строк с ALL, затем удалено 80 строк с ALL. Автокомпакция временно отключена для наблюдения промежуточных состояний. На каждой реплике выполнен flush, а scylla sstable dump-data прочитал физические SSTables с явно переданной структурой таблицы. Счетчик учитывает поля tombstone в JSON, а не упоминания слова в путях файлов и не дублирующие shadowable_tombstone.

Сначала gc_grace_seconds=600 и tombstone_gc=timeout. После удаления выполнена major compaction до истечения grace. Затем repair успешно завершен на всех узлах. Только после этого grace экспериментальной таблицы уменьшен до нуля и major compaction повторена на всех репликах. В конце grace=600 и автокомпакция восстановлены. Рабочие три таблицы сохраняют gc_grace_seconds=864000.

| Этап | Видимые строки | Tombstones на узлах 1/2/3 | Размер JSON узла 1, байт |
| --- | --- | --- | --- |
| До DELETE | 100 | 0 / 0 / 0 | 21433 |
| После DELETE | 20 | 80 / 80 / 80 | 42142 |
| Compaction до grace | 20 | 80 / 80 / 80 | 24963 |
| Repair + grace=0 + compaction | 20 | 0 / 0 / 0 | 4493 |

Размер JSON показывает объем диагностического представления, а не размер SSTable на диске. В сохраненных дампах после удаления присутствуют старые данные и маркеры; после ранней compaction остаются маркеры; после repair и финальной compaction их нет, а 20 живых строк сохраняются. Вывод подтвержден отдельно на каждой реплике. Файлы перечислены в output/evidence/tombstones.json. Финальная проверка выполнена офлайн по 12 сохраненным дампам: сравниваются timestamp живого значения и удаления. Это повторный анализ ранее снятых данных, не новый замер.

Уменьшать grace в рабочей системе без контроля repair опасно: реплика, пропустившая удаление, может вернуть старое значение после исчезновения маркеров на остальных узлах. В данном опыте все узлы доступны, удаление выполнено с ALL, repair завершен до ускоренной сборки. Эксперимент демонстрирует механизм физического удаления; самостоятельное истечение 600 секунд не ожидалось. Параметры tombstone_gc новых версий могут отличаться, поэтому timeout задан явно.

## 7. Нагрузочный эксперимент

Отдельный прогон выполняет 10 000 логических записей и затем 10 000 чтений с 16 потоками, ONE/QUORUM, на трех здоровых узлах. Каждый write изменяет три таблицы, то есть всего выполняется 30 000 INSERT. Учитываются wall-clock время фазы, число успешных операций, средняя задержка и p95. Прогрев исключен. Это ограниченный локальный тест, не поиск максимальной устойчивой пропускной способности и не длительный soak test.

| Операция | Успешно | Mean / p95, мс | Throughput, оп/с |
| --- | --- | --- | --- |
| Logged batch ONE | 10000/10000 | 1.529 / 2.636 | 10260.4 |
| SELECT QUORUM | 10000/10000 | 3.129 / 5.063 | 5049.5 |

Метрики приведены непосредственно из output/evidence/load.json, где сохранены все измерения. Производительность трех независимых физических узлов из этих данных вывести нельзя. Низкая кардинальность result создает горячий раздел; после добавления горизонтального шардирования план чтения потребовал бы слияния нескольких потоков.

## 8. Проверки и воспроизведение

Автотесты Java проверяют прежние сервисы и контроллеры, работу контекста, новое курсорное чтение, ошибки запросов, захват успешных/неуспешных операций и изоляцию сбоя аудита. Сохранены проверки CouchDB validation/MapReduce и миграции. Живой integration.py проверяет прежний бизнес-сценарий с реальными CouchDB/Etcd; новые сценарии проверяют ScyllaDB. Точные результаты и данные экспериментов находятся в output/evidence.

```bash
podman compose up --build -d
./gradlew test bootJar
node scripts/test_database_rules.cjs
python3 scripts/test_migration.py
python3 scripts/integration.py
python3 scripts/scylla_integration.py
python3 scripts/scylla_boundaries.py
python3 scripts/scylla_experiments.py --count 300 --workers 8
python3 scripts/tombstone_experiment.py
python3 scripts/load_experiment.py --count 10000 --workers 16
python3 scripts/write_report.py
.venv/bin/python scripts/build_report.py
```

Для Docker перед экспериментами задается CONTAINER_ENGINE=docker. Эксперименты выполняются последовательно. Контейнеры имеют постоянные volumes; повторный запуск добавляет уникальные тестовые данные. Удалять volumes для повторения не требуется.

Во время подготовки стенда 20 GiB диск локальной VM заполнился образами и служебными данными. Обнаружена ошибка No space left on device. Виртуальный диск увеличен до 40 GiB; раздел и файловая система остаются 20 GiB до отдельного разрешения на расширение. После перезапуска повторены интеграционные проверки. Нагрузочный прогон завершился до заполнения диска. Итоговые evidence-файлы содержат реальные завершенные измерения; tombstones.json явно указывает повторную проверку сохраненных дампов, а не новый прогон. VM выделено 4 vCPU и 6 GiB RAM.

## 9. Выводы и ограничения

Приложение дополнено ScyllaDB без замены CouchDB и Etcd. Три таблицы соответствуют трем запросам, дневные UTC-бакеты и timeuuid позволяют читать период в заданном порядке и продолжать по курсору. Назначенная пара ONE/QUORUM выдержала остановку одной реплики, но не дает гарантии read-after-write при RF=3. ALL теряет доступность после остановки одной реплики. Tombstones наблюдались в SSTables после логического удаления и исчезли после безопасной в условиях опыта сборки. Нагрузочные показатели измерены и сохранены вместе с исходными выборками.

Не реализованы durable outbox, аутентификация, snapshot-пагинация и автоматическое обслуживание repair. При полном отказе Scylla события аудита могут потеряться, хотя прежние бизнес-операции продолжают работать. Один локальный VM-стенд ограничивает применимость результатов производительности. Эти ограничения не скрываются за результатами unit-тестов или единичного успешного чтения.
