# Лабораторная №3 — ScyllaDB

Вариант **7809**. Продолжение лабораторной №2 на Java 17 и Spring Boot. Прежние API, CouchDB и Etcd сохранены; ScyllaDB хранит журнал выполнения бизнес-операций.

## Что делает приложение

В приложении можно создавать события библиотеки, оформлять временные заявки и заказы, сохранять настройки менеджеров и учитывать просмотры.

- **CouchDB** хранит документы событий, заказов и настроек, поддерживает ревизии, поиск и репликацию.
- **Etcd** хранит временные заявки с TTL, счётчики просмотров и кэш настроек.
- **ScyllaDB** хранит результаты выполнения операций: успех или ошибку, название операции, объект, время и HTTP-код.

В лабораторной исследуются репликация, уровни согласованности, отказ одной реплики, образование и удаление маркеров удаления (tombstones), а также пропускная способность и задержки.

## Запуск на компьютере

Понадобится Docker с Compose либо Podman с Compose. Для виртуальной машины рекомендуется 6 ГиБ оперативной памяти и не менее 10 ГиБ свободного дискового пространства. Java и Gradle для запуска через контейнеры отдельно устанавливать не нужно: сборка выполняется внутри контейнера.

Из папки проекта:

```bash
# Если используется Docker:
docker compose up --build -d
```

Для Podman на macOS:

```bash
podman machine list
# Запустить свою виртуальную машину, если она остановлена:
podman machine start podman-applehv-test
podman compose up --build -d
```

Первый запуск требует загрузки образов и сборки приложения. Сначала поднимаются базы данных, затем создаются таблицы и запускается приложение.

Откройте **http://localhost:18080/**. Журнал находится во вкладке **«Бизнес-операции»**.

CouchDB доступна по адресу http://localhost:5984/_utils/, её реплика — на порту 5985. Учебные логин и пароль: `library` / `library`. Etcd использует порт 2379. Если эти порты заняты контейнерами предыдущих лабораторных, сначала остановите их.

Проверка состояния и просмотр журнала приложения:

```bash
podman compose ps
podman compose logs --tail=100 app
podman compose exec scylla1 nodetool status
```

В выводе `nodetool status` должны быть три узла со статусом `UN`: доступны и работают в обычном состоянии. Службы `setup` и `scylla-setup` завершаются после настройки; код завершения 0 означает успех. Для Docker замените `podman` на `docker`.

Остановка с сохранением данных:

```bash
podman compose down
```

Не добавляйте `-v`, если хотите сохранить данные. Проект использует отдельные постоянные тома `lab3`. Порты привязаны к локальному компьютеру; конфигурация предназначена для учебного стенда.

## Как показать работу

1. Создайте событие библиотеки.
2. Создайте для него заявку и оформите заказ.
3. Откройте «Бизнес-операции», выберите результат `SUCCESS` и период, включающий текущее время.
4. Найдите записи о создании события, заявки и оформлении заказа.
5. Попробуйте оформить отсутствующую заявку: операция завершится ошибкой и появится запись `FAILURE`.
6. Проверьте сортировку и переход к следующей странице.

Прежние маршруты описаны в [инструкции лабораторной №2](docs/LAB2.md).

## Схема ScyllaDB

Три узла ScyllaDB 6.2.3, фактор репликации **RF=3**, запись с **ONE**, чтение с **QUORUM**. Каждый контейнер использует один вычислительный сегмент и 768 МиБ памяти. Это параметры локального учебного стенда.

| Запрос | Таблица | Ключ раздела | Ключ сортировки |
| --- | --- | --- | --- |
| События с заданным результатом за период | by_result | (result_key, day) | event_id timeuuid DESC |
| Выполнение заданной операции за период | by_operation | (operation_key, day) | event_id timeuuid DESC |
| История заданного объекта | by_entity | (entity_key, day) | event_id timeuuid DESC |

Каждый бакет соответствует одному календарному дню UTC. Запрос задаёт полный ключ раздела и диапазон времени; `ALLOW FILTERING` не используется. Полная схема: [scylla/schema.cql](scylla/schema.cql).

Дневной бакет ограничивает временной охват, но не максимальный размер раздела: при высокой нагрузке раздел с результатом SUCCESS может стать горячей точкой. Для дальнейшего масштабирования потребовалось бы дополнительное разделение данных и объединение результатов чтения.

## Чтение журнала через API

```bash
curl -G http://localhost:18080/api/business-events \
  --data-urlencode 'result=SUCCESS' \
  --data-urlencode 'from=2026-11-19T00:00:00Z' \
  --data-urlencode 'to=2026-11-20T00:00:00Z' \
  --data-urlencode 'sort=desc' --data-urlencode 'limit=20'
```

Подставьте период, за который вы создавали данные. Требуется ровно один фильтр: `result`, `operation` или `entity`.

- `from` включается, `to` исключается. Формат ISO-8601 с часовым поясом, точность до миллисекунд, период не более 31 дня.
- `sort=asc` — сначала старые записи; `sort=desc` — сначала новые.
- `limit` — от 1 до 200, по умолчанию 50.
- Ответ содержит `events` и `nextCursor`. Значение `null` означает конец выборки.
- Для продолжения передайте `cursor` с прежними фильтром, периодом и направлением сортировки. Размер страницы можно менять.

Курсор содержит полный timeuuid: события с одинаковым временем в миллисекундах не теряются. Пагинация не фиксирует снимок данных при параллельных записях.

Записываются операции CREATE_EVENT, UPDATE_EVENT, DELETE_EVENT, REGISTER_VIEW, CREATE_DRAFT, SUBMIT_DRAFT и SAVE_SETTINGS. Чтения и технические эксперименты Etcd не создают записи аудита. Для SUBMIT_DRAFT идентификатор объекта — ID заявки, а не заказа; для неуспешного создания без ID используется `collection`. Повторное оформление одной заявки создаёт новую запись о попытке, сохраняя прежний заказ.

`GET /api/business-events/status` показывает состояние аудита и счётчики записей и ошибок за время работы процесса.

## Согласованность и ограничения

При RF=3 ONE ожидает одну реплику, QUORUM — две, ALL — три. Пара ONE/QUORUM выдерживает отказ одной реплики, но не гарантирует чтение последней записи: сумма 1+2 не превышает RF.

Три денормализованные копии события записываются журналируемым пакетом. Общей транзакции между CouchDB, Etcd и ScyllaDB нет. При полном отказе ScyllaDB уже выполненная бизнес-операция сохраняет свой результат, а ошибка аудита записывается в журнал и счётчик. Постоянной очереди повторной доставки нет: при полном отказе или падении процесса часть событий может потеряться.

Если ScyllaDB включена, но недоступна при первоначальном подключении, приложение не запустится. Для запуска прежней функциональности без неё можно задать `SCYLLA_ENABLED=false`.

## Проверки и эксперименты

```bash
# Проверки Java; локально требуется JDK 17:
./gradlew test bootJar
node scripts/test_database_rules.cjs
python3 scripts/test_migration.py

# Проверки работающего приложения:
python3 scripts/integration.py
python3 scripts/scylla_integration.py
python3 scripts/scylla_boundaries.py

# Эксперименты запускаются последовательно:
python3 scripts/scylla_experiments.py --count 300 --workers 8
python3 scripts/tombstone_experiment.py
python3 scripts/load_experiment.py --count 10000 --workers 16
```

Для Docker задайте `CONTAINER_ENGINE=docker` перед запуском сценариев экспериментов. На macOS для локальной сборки при необходимости используйте `JAVA_HOME=$(/usr/libexec/java_home -v 17)`.

Сценарий согласованности сравнивает разные уровни при трёх работающих репликах, временно останавливает только `scylla3` проекта `lab3`, ожидает состояния 2 UN + 1 DN и повторяет измерения. В блоке `finally` узел запускается обратно.

Эксперимент с маркерами удаления создаёт отдельную таблицу, записывает 100 строк с ALL и удаляет 80. На каждой реплике сохраняются физические дампы SSTable до удаления, после удаления, после раннего слияния файлов и после синхронизации реплик и окончательной очистки. Период удержания временно уменьшается только у экспериментальной таблицы, после успешной синхронизации. Рабочие таблицы сохраняют `gc_grace_seconds=864000`.

Нагрузочный сценарий измеряет пропускную способность, среднюю задержку и p95. Одна запись — пакет изменений трёх таблиц, одно чтение — до 50 строк. Это измерения CQL-клиента внутри локальной виртуальной машины; HTTP, CouchDB и Etcd в них не входят. Результаты не являются оценкой производительности промышленного кластера.

Сырые результаты находятся в `output/evidence/`. Итоговая проверка маркеров удаления повторно анализирует 12 сохранённых дампов завершённого опыта:

```bash
python3 scripts/verify_tombstone_dumps.py tombstone_0b6891cd7d4f
```
